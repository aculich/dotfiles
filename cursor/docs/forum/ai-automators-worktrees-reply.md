Great writeup — "worktrees copy the codebase, they do **not** copy all the services around the codebase" is exactly the right framing, and your ledger (ports isolated, heavy deps shared, DB shared, test accounts isolated) matches what we converged on too.

One thing I'd add from running this workflow inside Cursor: there's a **second ledger** beyond the runtime services — the **IDE and agent layer** also doesn't copy cleanly into a worktree. A few things we hit:

**1. Editor identity follows the path, not the branch.** Cursor (like VS Code) keys workspace state — chat history, some UI state — to the folder path. Every worktree is a new path, so it's a fresh workspace identity: no chat history, fresh index. Anything you want an agent to know in *any* worktree has to be **committed**: rules files, a WORKTREES.md like yours, saved plan files. Your instinct to write WORKTREES.md was right for a deeper reason than documentation — it's effectively the only context that survives the copy.

**2. You can replace the port-offset bookkeeping with names.** Your offset scheme (8002/5174, 8003/5175, …) works, but there's a tool that dissolves the problem: [portless](https://github.com/vercel-labs/portless) (Vercel Labs). It runs your dev servers behind a local HTTPS proxy with named `.localhost` URLs — and it detects git worktrees natively, prepending the branch name as a subdomain. So the main checkout serves `https://myapp.localhost`, and a worktree on branch `fix-ui` automatically serves `https://fix-ui.myapp.localhost`, no per-tree config. Each app gets a random free port under the hood; nobody (human or agent) tracks offsets anymore. Three bonus effects for parallel agents: agents stop guessing or hardcoding ports when validating; each worktree is a distinct browser *origin*, so cookies and localStorage from one agent's test session don't bleed into another's; and `portless get <name>` gives scripts a stable way to wire services together. It's the same mental model as Cloudflare Pages branch deploys or Vercel preview URLs — every branch gets its own stable address — except local: worktree + portless ≈ a preview environment on your laptop.

**3. Your ignore files are a map of what a new worktree won't contain.** A worktree checks out *tracked* files only — everything gitignored stays behind in the main tree. That cuts both ways. The good side is by design: each tree is a clean room, and it flushes out hidden dependencies on untracked state you didn't know you had. The surprise side: if development relies on untracked paths — `.env` files, gitignored vendored clones or subrepos (we keep reference repos under an ignored `upstream/`), large data files, generated artifacts, local caches — they're silently absent in the new tree, and an agent fails in confusing ways ("module not found," empty fixtures, tests that pass in main and fail in the worktree). Your venv symlink is one instance of the general rule: **every ignored-but-load-bearing path needs an explicit decision** — symlink it back (heavy, shared), copy it (cheap, mutable), regenerate it in the setup script (env files, codegen), or document that worktrees can't do that class of work. We now audit `.gitignore` when designing the setup script, because it doubles as the checklist of what the script must recreate. Separately, the editor-side ignore files (`.cursorignore`, watcher excludes) multiply across trees: if they're committed they travel for free; if they live in user settings, every worktree re-indexes your venvs and `node_modules` before you notice.

**4. Cursor now has first-class worktree support worth knowing about even if you don't use Cursor.** `/worktree` spins up an isolated checkout per chat, `/apply-worktree` merges back, and `.cursor/worktrees.json` runs a committed setup script in each new tree (your `setup-worktree.ps1`, but declared in config so the agent runs it automatically). There's also `/best-of-n` — same task, N models, N worktrees, pick a winner — which is great for genuinely ambiguous tasks and a money bonfire for everything else.

**5. Verify isolation, don't assume it.** Early community reports on Cursor's worktree features included runs that *looked* isolated but weren't, and setup scripts that silently didn't fire. We now treat every worktree run as: confirm baseline (tests/lint pass in the fresh tree), then work, then re-validate before applying back. Cheap insurance.

**6. Parallelism multiplies spend, not just throughput.** Once N agents run concurrently, model routing becomes a real decision: cheap/default models for mechanical worktree tasks, premium models pinned only on the one or two trees doing interpretive work, and a check of the usage dashboard between merge waves. The same wave discipline you use for merging works for budgets.

Your merge flow (main checkout parked on master, review each branch, merge, remove the worktree) matches ours, with one addition: **apply one worktree at a time and re-run validation after each apply**, even when the diffs look disjoint. Two agents that never touched the same file can still break each other through a shared schema or config.
